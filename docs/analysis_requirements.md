# Анализ и требования. Система учета заявок на общежитие

**Автор:** Дюсембаев Дамир, ИС 25-22

## 1. Анализ предметной области
Студенты подают заявки на общежитие перед учебным годом. Заявок много, они приходят в разное время и проходят рассмотрение. Основные проблемы ручного учёта: потеря заявок, ошибки и пропуски данных, дубли, отсутствие прозрачного статуса и истории решений.

**Актуальность.** По данным заседания фракции Respublica, из 678 тыс. студентов Казахстана 364,5 тыс. иногородние (BES.media). Государство развивает онлайн-подачу заявок через eGov.kz (inbusiness.kz, nur.kz), обсуждаются платформы выбора комнат (UniDorm 2.0), а вузы используют информационные системы вроде Platonus (Informburo.kz).

**Аналоги:** eGov.kz, UniDorm 2.0, Platonus, ручной учёт по правилам вуза. Сравнение и ссылки — в README, раздел 2.

**Вывод:** нужен лёгкий инструмент для внутреннего учёта заявок с проверкой ввода и контролем статусов.

## 2. Требования
**Функциональные**
- ФТ-1. Подача заявки с проверкой полей.
- ФТ-2. Просмотр списка и сортировка (id, ФИО, курс, дата, статус).
- ФТ-3. Поиск по ФИО/билету, фильтр по статусу и факультету.
- ФТ-4. Смена статуса только по допустимым переходам.
- ФТ-5. История изменений, статистика, удаление.
- ФТ-6. Запрет второй активной заявки одного студента.

**Нефункциональные**
- НФТ-1. Python 3.8+ без внешних зависимостей.
- НФТ-2. Сохранность данных между запусками (JSON).
- НФТ-3. Понятные сообщения об ошибках, повторный запрос при неверном вводе.
- НФТ-4. Устойчивость: приложение не завершается аварийно при пустом вводе.

**Пользовательские сценарии**
1. Студент подаёт заявку, при ошибке ввода повторяет поле и получает номер заявки.
2. Сотрудник ищет заявку, переводит в «На рассмотрении», затем в «Одобрена» или «Отклонена».
3. Сотрудник сортирует список по курсу или ФИО и смотрит статистику и историю.

**Критерии приемки:** все автотесты PASS; некорректные данные не попадают в базу; недопустимый переход статуса блокируется; история фиксирует каждое изменение.

## 3. Модель жизненного цикла: инкрементная
Проект небольшой, требования понятны, но удобно наращивать функциональность и проверять каждый шаг тестами:
1. Инкремент 1 — модель данных и валидация.
2. Инкремент 2 — добавление, поиск, сортировка.
3. Инкремент 3 — статусы, история, статистика.
4. Инкремент 4 — JSON-хранилище и консольное меню.
5. Инкремент 5 — тестирование, исправление дефектов D1–D4.

Каскадная модель менее гибка при исправлениях, спиральная избыточна для проекта такого размера.

## 4. Проектирование
- **Модули:** валидаторы → `Application` и `Status` → `DormRegistry` → JSON → меню.
- **Структуры данных:** список объектов dataclass, `Enum` для статусов, словарь допустимых переходов `TRANSITIONS`, список строк для истории.
- **Ключевые алгоритмы:** регулярные выражения для ФИО и телефона; линейный поиск и фильтрация в цикле; сортировка по ключу через словарь функций; цикл повторного ввода до корректного значения; проверка перехода статуса по таблице.

## 5. Связь с лекциями 1-8
Циклы (меню, повторный ввод), функции (валидаторы, методы), массивы и коллекции (списки, словари), строки и библиотеки (`re`, `json`, `datetime`), структуры и перечисления (`dataclass`, `Enum`), жизненный цикл ПО (инкрементная модель, тестирование).
